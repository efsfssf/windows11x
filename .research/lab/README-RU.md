# Windows 11X — новый V6+embedded V7 API Set (ОФЛАЙН-КАНДИДАТ)

## Ключевое

Это **не загрузочный пакет** и **не работающая WCOS**. Файл `ApiSetSchema-Windows11X-26100-OFFLINE-UNSIGNED.dll` — экспериментальный PE на базе **точного** оригинального `ApiSetSchema.dll` версии 26100.9278 (SHA-256 `391a2818...e480889`).

Уже было доказано в предыдущем TraceSmoke/WinDbg, что `BaseApiSetSchema` позволяет выбрать альтернативный PE, но **прошлая V6-only правка терялась при построении активной схемы из embedded V7**. Новый кандидат меняет оба представления согласованно.

## Что конкретно изменено

| Контракт | Host V6 | Host embedded V7 | SEALED |
|---|---|---|---|
| `ext-ms-win-ntos-stateseparation-l1-1-0` | `statesepext.sys` | `statesepext.sys` | сохранён |
| `ext-ms-win-core-stateseparationext-l1-1-0` | `onecorestateseparationext.dll` | `onecorestateseparationext.dll` | сохранён |

Старый namespace V6 и встроенный V7 теперь ссылаются на одну и ту же строку для каждого Host. Сохранено 984 legacy-контракта; 982 legacy значения побайтово не изменены. В V7: 984 version records и исходные hash-lookup таблицы, 286 старых Host records + 2 новых, пересчитанная Host hash-index таблица, string pool и соответствующие смещения. Размер нового namespace `0x29CE0` вместо `0x29C60`; PE размер остался неизменным (194016 байт). `SEALED` флаги не сбрасывались.

Для самостоятельной проверки: `Verify-Offline-APISet.ps1` проверяет SHA, V6/V7 размеры, оба Host, флаги и количество записей. **Не требует администратора, не изменяет Windows и не загружает DLL.** Сборщик `build_dual_schema.py` требует Python 3 и `v7_decode.py` из пакета; принимает только hash-pinned исходный PE.

## Почему пока НЕЛЬЗЯ заменять или загружать этот файл при старте VM

1. Изменение `.apiset` внутри PE нарушило оригинальную криптографическую идентичность образа. Пересчёт PE checksum **не восстанавливает Microsoft-подпись**. Ранний загрузчик 26100 проверяет соответствие образов политике доверия; в наших исследованиях для базы и расширения обнаружен отдельный early-image signing scenario 1.
2. В текущем обычном 26100 отсутствуют `statesepext.sys` и `onecorestateseparationext.dll`. Для DLL-контракта нет нативного доверенного Host. `statesepext.sys` 22000 по именам импортов соответствует ядру 26100 (26/26), но ABI/runtime/инициализация не доказаны.
3. Даже если файл с новым V7 mapping будет прочитан, это не доказывает успешную загрузку SYS или вызов Phase0. В TraceSmoke был разрешён исследовательский путь под подключённым boot debugger, но **это не доказанный автономный путь запуска без WinDbg**.
4. Не выполняйте прямую замену `C:\Windows\System32\ApiSetSchema.dll`, не добавляйте экспериментальный `BaseApiSetSchema`, не копируйте 22000 SYS в ядро 26100 и не активируйте `StateSeparation\Policy\Enabled=1`. Это может остановить загрузку даже тестовой VM.

## Что требуется для первого настоящего boot теста

- **Trusted schema gate:** подтверждённый разрешённый политикой загрузки способ принять эту или другую согласованную V6/V7-схему в изолированной VM. Boot debugging может дать диагностический путь, но не является решением для штатной загрузки.
- **Host gate:** совместимые и доверенные ранние `statesepext.sys` и `onecorestateseparationext.dll`, либо ограниченный специально разработанный диагностический host для измерения привязки (не для реальной WCOS), принятый конкретной boot policy.
- **Kernel state gate:** подготовленные доступные на нужном этапе `OSBOOT`, `DEVICES`, `OSDATA`, `OSDataRoot`, корректные BCD/хранилища и сопоставленные ABI/Phase0/1/2.
- **Rollback gate:** проверенный отдельный Hyper-V checkpoint/восстановление, подтверждённый boot baseline, не трогать исходную 26100 и Factory OS.

**WinDbg не нужен для проверки офлайн-файла.** Для доказательства именно ранней привязки/отказа WinDbg или эквивалентная ранняя трассировка нужна, потому что обычная система может вообще не загрузиться, не оставив достаточно логов. Без доверенного boot path тест загрузки не рекомендуется ни с WinDbg, ни без него.
