# Один минимальный read-only диагностический след

Если понадобится закрыть оставшийся вопрос о **конкретной** загрузке, достаточно одного trace boot с тремя последовательными read-only снимками уже выделенных буферов WinDbg:

1. Сразу после копирования `.apiset` по `winload` RVA `0x231EA`, до unload/compose: зафиксировать размер, SHA-256 либо полный дамп **скопированного** namespace и байты `+0x1C/+0x20`, Trace value `+0x94F0`, UTF-16 span `+0x29C60`. Сравнение с приложенным B однозначно проверит источник.
2. Непосредственно перед `call OslpApplyDynamicSchemaExtensions` по `0x2335F`: сохранить текущий pointer/size и namespace buffer для offline сравнения с первым снимком. Это отделяет загрузку и registry composition от последней динамической стадии.
3. После возврата из **того же** вызова, перед handoff по `0x23375`: сохранить pointer/size и namespace buffer; сравнить с предыдущим и проверить Trace V7 mapping/выходную длину offline. На этом этапе достаточно памяти и лога; вызов resolver вручную не нужен.

**Различающие исходы:** если первый снимок совпадает с B, его legacy Host действительно поступил в загрузчик; если не совпадает — первична ошибка источника/копии. Если B совпадает, но второй снимок уже не содержит resolver-visible Host, расхождение произошло до dynamic extension (embedded V7 selection и/или registry composition). Если второй содержит host, а третий пуст — решающая стадия dynamic extension. Если размер меняется `0x29C60→0x29C74` именно между вторым и третьим снимками, это подтверждает рассчитанную добавку `0x14`; если нет, совпадение конечного размера требует другого объяснения.

Снимки выполняются в **одной** загрузке только чтением памяти и существующего лога. Не нужны новый PE/SYS, изменение guest/BCD/политик, установка драйвера или обход trust. Для интерпретации полного V7 mapping может понадобиться отдельный offline decoder; не подменять его чтением одного legacy value.
