# Решение — NO-GO на первый boot NT 26100.9457

**2026-11-08. Критерий этапа не выполнен:** на предоставленном наборе нет доказанного доверенного пути ранней привязки совместимых Phase0/1/2. PoC01 оставлена без изменений. Это решение для имеющихся артефактов и допустимой цепочки доверия, а не утверждение о невозможности любых закрытых OEM-конфигураций.

**Блокер локализован.** `BaseApiSetSchema` действительно выбирает другой schema PE: `winload` 26100.9444, `0x23111 → 0x23175 → 0x231A9 → 0x233C8 → OslLoadImage`. После принятой схемы ранний путь host существует: `OslpLdrExOverrideImport 0x1BCEC → ApiSetResolveToHost 0x279130 → LdrpLoadImage → BlLdrBindImportReferences`. Значит, проблема не в отсутствии механизма выбора или раннего импорта. Не хватает **принятой boot policy согласованной схемы и совместимого принятого extension**, а не ещё одного registry switch.

**Почему собственной подписи недостаточно.** При обычных включённых проверках целостности `OslInitializeCodeIntegrity` выбирает policy3 (`0x17731–0x17745`, store `0x17C6D`); schema получает signing scenario1 (`0x1C2B0`, `0x198B5A–0x198B60`). В `ImgpValidateImageHash` расширение корней Custom Kernel Signers достижимо только для scenarios **{2,3,4,7}** (`0x197927–0x197965`), scenario1 его пропускает. Ранний kernel API Set host наследует loader context `0x110` и также попадает в scenario1 (`0x1BE98 → 0x19D7FE → 0x1C168–0x1C180`). Документированная Microsoft возможность собственного обычного kernel signer поэтому не является разрешением ни схемы, ни этого early host. Policy1 связана с DisableIntegrityChecks и исключена условиями проекта. Дополнительно basename проверяется против `OriginalFilename` (`0x1959BB`), mismatch → `0xC0430007`. Полная трасса и пределы вывода — `WINLOAD-26100-9444-CALLGRAPH.md`, `evidence/boot-trust.md`.

**ABI не объявляется несовместимым.** Реальные 26100 callers согласуются с 22000: Phase0 `(BOOLEAN Enabled, BOOLEAN DevelopmentMode)`, Phase1 `(BOOLEAN Enabled)`, Phase2 `(BOOLEAN Enabled, PCUNICODE_STRING Source, PCUNICODE_STRING Target)`. Phase2 — условный WNF callback, не обязательная третья ступень boot. Однако жизненный цикл INIT, сериализация, доступность OSBOOT до Phase0 и OSDataRoot до Phase1 не доказаны для этой конфигурации. Оригинальная Phase0 создаёт/дополняет target, GUID-переименовывает source, ставит volatile REG_LINK; в исследованных error paths **нет rollback**. Успешная заглушка не заменяет эти действия.

**Источник не закрыт.** Все восемь приложенных boot CAB — 22000.1 amd64; проверенный публичный WSK download ведёт к 22000. Подлинного согласованного PC WCOS26100 комплекта не установлено. Это не доказывает отсутствия закрытого выпуска и не доказывает, что при всех возможных официальных политиках требуется исключительно внутренняя подпись Microsoft. Но приемлемого собственного signing/provisioning route для exact scenario1 и конкретного кандидата также нет.

**Принятый маршрут:** сохранить цель NT26100; переходить к загрузке только после получения конкретной официальной PC x64 composition либо отдельно доказанного официального scenario1 signing/provisioning пути. Следующий практический шаг — предъявить Microsoft/OEM спецификацию `OEM-COMPONENT-REQUEST.md` и получить проверяемый кандидат, затем прогнать offline acceptance. Если получить его невозможно, ранний boot26100 остаётся NO-GO; Factory22000 остаётся эталоном семантики. Сейчас допустимы комплектные офлайн-проверки и модель; `NEXT-BOOT-EXPERIMENT.md` прямо запрещает boot test до закрытия предусловий.
