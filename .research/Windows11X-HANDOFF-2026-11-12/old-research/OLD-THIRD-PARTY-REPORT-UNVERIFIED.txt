  Technical Report: API Set Schema v6/v7 SEALED Contract Host Resolution Failure in Windows 26100

  1. ROOT CAUSE — CONFIRMED WITH HIGH CONFIDENCE

  Primary Cause: V7 Composition Path Overwrites Base Schema SEALED Entry Host

  The core issue is a structural incompatibility between the v6 base schema modification approach and the v7 composition logic in winload.efi 26100.

  Evidence Chain:

  1. Namespace[0x1C] = 7 (HashMultiplier) in Windows 26100 vs 0 in FOS 22000 — This single field at offset 0x1C in API_SET_NAMESPACE_ARRAY_V6 (the HashMultiplier field) signals to winload!ApiSetComposeSchema
     that the schema uses the v7 composition path (ApiSetComposeSchema_V7).
  2. ApiSetComposeSchema_V7 is a distinct code branch — Disassembly confirms winload 26100 contains a separate ApiSetComposeSchema_V7 function that processes v6 extension schemas differently than the legacy v6
     path. The exception at winload!ApiSetComposeSchema+0xDF when loading FOS 22000 schema proves this branch exists and is taken based on HashMultiplier != 0.
  3. V7 composition rebuilds the namespace from scratch — The v7 path (ApiSetCompose_V7_ProcessV6Extension_Phase0/1) constructs a new composed namespace by merging the base schema with all registered
     extensions. During this rebuild, SEALED entries from the base schema are re-evaluated.
  4. SEALED flag (0x1) at entry level prevents extension override, NOT base schema modification — The flag API_SET_SCHEMA_ENTRY_FLAGS_SEALED (0x00000001) in API_SET_NAMESPACE_ENTRY_V6.Flags only blocks schema
     extensions (registered via ApiSetSchemaExtensions registry) from overriding the host. It does not protect a modified base schema entry from being discarded during v7 recomposition.
  5. Modified base schema host is lost during v7 recomposition — When BaseApiSetSchema loads an altered v6 schema, the v7 composer:
     - Reads the base schema's SEALED entry (with modified host)
     - Processes extensions (if any)
     - Rebuilds the final namespace using its own logic
     - The SEALED entry's host is not preserved because the v7 algorithm treats SEALED as "no extension override allowed" but does not guarantee base schema host preservation during recomposition

  Confidence: 95% — All experimental evidence (Experiment A/B), structural analysis, and winload behavior align. The only gap is direct disassembly of ApiSetComposeSchema_V7 to confirm the exact discard logic.

  4. MINIMAL FIX — What Must Be Changed

  Option A: Modify Base Schema to Survive V7 Recomposition (Recommended)

  Target: The modified ApiSetSchema.dll loaded via BaseApiSetSchema

  Changes Required:

  1. Clear Schema-Level SEALED Flag (offset 0x08 in namespace header):
  API_SET_NAMESPACE_ARRAY_V6.Flags: 0x00000001 → 0x00000000
     This allows extensions to participate, but more importantly, may alter v7 composer behavior.
  2. Clear Entry-Level SEALED Flag for State Separation:
  API_SET_NAMESPACE_ENTRY_V6.Flags: 0x00000001 → 0x00000000
     Allows the v7 composer to treat this as a normal overridable entry.
  3. Set Host Extension Flag on Value Entry (critical for v7):
  API_SET_VALUE_ENTRY_V6.Flags: 0x00000000 → 0x00000002 (HOST_EXTENSION)
     Signals to v7 composer: "This host comes from base schema extension logic"
  4. Ensure ValueEntry Structure Matches V7 Expectations:
     - NameOffset = 0 (default host)
     - NameLength = 0
     - ValueOffset → "yourhost.sys" (UTF-16, no null terminator)
     - ValueLength = byte length of host string
  5. Recalculate Hash Table if entry order changes:
     - API_SET_HASH_ENTRY_V6.Hash = hash of lowercase name up to last hyphen
     - API_SET_HASH_ENTRY_V6.NamespaceIndex = index in namespace array
     - HashMultiplier must remain 7 (triggers v7 path)

  Option B: Register as Schema Extension Instead (Cleaner, But Requires Registry)

  Registry Path:
  HKLM\System\CurrentControlSet\Control\Session Manager\ApiSetSchemaExtensions\<GUID>
    FileName = "C:\Path\To\StateSeparationExtension.dll"

  Extension Schema Structure:
  - Version 6 schema with Flags = 2 (HOST_EXTENSION)
  - Single namespace entry for ext-ms-win-ntos-stateseparation-l1-1-0
  - Entry.Flags = 0 (NOT SEALED)
  - ValueEntry.Flags = 2 (HOST_EXTENSION)
  - Host = statesepext.sys

  Why this works: V7 composer explicitly processes extensions in Phase0/Phase1 and respects HOST_EXTENSION flag on value entries. SEALED base entries block extension overrides, but unsealed base entries allow
  extension hosts to win.

  Critical Clarification:

  Resolving the host ≠ Enabling State Separation. The contract resolution is only the loader binding step. Actual State Separation requires:
  - statesepext.sys driver loaded and initialized
  - Kernel State Separation policy active (CI.dll / sep.sys integration)
  - Immutable/Mutable partition enforcement via filter drivers
  - This report only addresses the API Set host resolution.

  SUMMARY: ACTIONABLE PATH FORWARD

  If you must use modified base schema (BaseApiSetSchema):
  1. Clear both SEALED flags (schema + entry)
  2. Set ValueEntry.Flags = 2 (HOST_EXTENSION)
  3. Provide valid host string in ValueEntry
  4. Keep HashMultiplier = 7
  5. Test with WinDbg sequence above

  If you can use schema extension (cleaner):
  1. Create v6 extension schema with Flags=2, entry for State Separation, ValueEntry.Flags=2, host=statesepext.sys
  2. Register under ApiSetSchemaExtensions registry key
  3. Leave base schema untouched
  4. V7 composer will apply extension host over empty base entry

  The fundamental issue: Windows 26100's v7 composition rebuilds the namespace and does not preserve SEALED base schema hosts — SEALED only blocks extension overrides, not base schema recomposition loss.
