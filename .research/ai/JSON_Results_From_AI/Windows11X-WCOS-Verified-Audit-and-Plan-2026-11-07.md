# Windows 11X / WCOS 26100 — сверенный технический статус и план

**Дата пересмотра:** 2026-11-07  
**Задача:** настоящая Windows Core OS с современными согласованными компонентами NT 26100 на x64 / Hyper-V Gen2; State Separation, защищённый MainOS, персистентный OSData и перенос необходимого состояния реестра. Оболочка Santorini, OOBE, UWP/WinUI и Win32-контейнеры — после доказательства WCOS Core.

## 1. Метод и уровень проверки

Сверены 18 загруженных аналитических Markdown/JSON/TXT-материалов и handoff 2026-11-05 с первичными локальными материалами (включая `WCOS-FullRegistry-22000.zip`, `WCOS-FullRegistry-26100.zip`, `WCOS-Reg-Factory22000.zip`, `WCOS-Reg-26100.zip`, `WCOS-KernelBoot-22000.zip`, `26100-WCOS-binaries.zip`, `WCOS26100-Boot-Interfaces.zip`, отдельные PE и REGF-файлы). Десять проверенных ZIP имели корректный CRC, включая `Windows11X-WCOS-2026-11-05-COMPLETE-HANDOFF.zip` с 78 членами. Это проверяет целостность ZIP, но не подлинность Microsoft-подписей или идентичность работающей ВМ.

- SHA-256 файлов `ntoskrnl.exe` для 22000/26100, `winload.efi` 22000/26100 (из ZIP), `statesepext.sys`, `cmimcext-26100.sys`, `XRo.sys`, `apisetschema-22000.dll` и `apisetschema-26100.dll` совпали с указанными в отчётах там, где хэши приведены.
- Независимо прочитан формат namespace `.apiset` v6 из обоих PE: 945 контрактов (22000) и 974 (26100).
- Независимо проверены таблицы PE экспортов и импортов: `statesepext` → NT 26100 **26/26**; `XRo` → NT 26100 **62/62**; `XRo` → FLTMGR 26100 **21/21**; `cmimcext` → NT 26100 **15/15**. Это *поимённая совместимость*, не ABI/runtime, подпись или поддерживаемость.
- Пересчитаны из сырых `.reg` ветки `StateSeparation`, `XRo`, `FeatureManagement`, `ApiSetSchemaExtensions`; цифры ниже совпадают с новыми сравнительными отчётами.
- Данные новых реальных остановок WinDbg 7 ноября сопоставлены с ранним статическим аудитом. Последние выводы WinDbg из чата являются динамическим свидетельством, но не заменяют повторение на второй независимой ВМ.

## 2. Что доказано динамически

### Factory OS 22000 (разделять ВМ `FOS-KD-Test` и `FOS-SS-Test`)

1. WinDbg на `FOS-KD-Test` обнаружил загруженный `statesepext.sys` (image range 0xD000) и **все три** реальных IAT-сопоставления `nt!_imp_ExpInitializeStateSeparationPhase0/1/2` → соответствующие экспорты `statesepext`.
2. При раннем `CmInitSystem0` на Factory OS аппаратная точка записи зафиксировала присваивание `CmStateSeparationEnabled=1` из таблицы `StateSeparation\Policy / Enabled`. В оригинальном конфиге параметр равен 1.
3. На клоне `FOS-SS-Test`: `XRo` зарегистрирован с `Start=0`, `RegistryFilterEnabled=1`, attached к MainOS (`M:`) и BSP (`B:`). Попытка записи на MainOS была отвергнута. Причина отказа не локализована исключительно до XRo.
4. После reboot файл на Data (`C:`) и прямая запись в `HKLM\OSDATA\SOFTWARE` сохранились. Экспериментальная запись в обычном `HKLM\SOFTWARE` исчезла; выбранное тестовое правило `RedirectionMap` **не доказало автоматическую переадресацию**. Не считать все правила исправными и не считать весь SOFTWARE заведомо volatile.

### Windows 26100 (Activation01)

1. На первой остановке `nt!DebugService2` пойман вызов `CmInitSystem0 → CmpGetSystemControlValues`.
2. В живой секции `INIT` у `nt+0xC34F80` найдена таблица из трёх записей: `Enabled`, `DevelopmentMode`, `AllHivesVolatile`, указатели на соответствующие глобальные переменные NT.
3. Во время обработки `Enabled` раздел `StateSeparation\Policy` обнаружен (`CmpWalkPath` вернул допустимый индекс ячейки `0x00AC0758`), но значение `Enabled` отсутствует (поиск вернул `0xFFFFFFFF`). Исполнение дошло до ветки пропуска; `CmStateSeparationEnabled=0`.
4. Phase0: WinDbg на реальном вызове `nt!IoInitSystemPreDrivers` показал `nt!_imp_ExpInitializeStateSeparationPhase0 → nt!DefaultAddProfileSource`, возврат `EAX=C00000BB`.
5. Phase1: в `nt!Phase1InitializationIoReady` импорт также ведёт к `DefaultAddProfileSource`, фактический `EAX=C00000BB`.
6. Phase2: при вызове по ветке `NtCreateWnfStateName → ExpWnfRegisterPermanentName → ExpWnfGetNameStoreRegistryRoot` импорт ведёт к той же заглушке, фактический `EAX=C00000BB`.
7. Все три вызывающих участка 26100 содержат явную обработку `STATUS_NOT_SUPPORTED`. Нельзя утверждать, что сама заглушка вызывает BSOD. Phase2 — поздний код WNF, а не обязательно отдельная фаза ранней загрузки.

**Итог динамики:** точки интеграции State Separation в NT 26100 существуют и реально исполняются, но **в исследованной штатной конфигурации не выполняют реализацию `statesepext.sys`**. Это не готовая WCOS 26100.

## 3. Самое существенное статическое различие

| Контракт в реальной `.apiset` namespace v6 | Factory OS 22000 | IoT LTSC 26100 |
|---|---|---|
| `ext-ms-win-ntos-stateseparation-l1-1-0` | `statesepext.sys` | пустой target |
| `ext-ms-win-core-stateseparationext-l1-1-0` | `onecorestateseparationext.dll` | пустой target |
| `ext-ms-win-ntos-kcminitcfg-l1-1-0` | пустой target | `cmimcext.sys` |

В реальной 26100 `cmimcext.sys` загружается, и его два экспорта разрешаются ядром. Следовательно, по крайней мере инфраструктура **некоторых** kernel extensions продолжает существовать. Но **не установлен** полный путь в `winload.efi`/boot loader, который выбирает, загружает и привязывает расширения. Установка target в API Set сама по себе не гарантирует загрузку, ABI-совместимость и правильную подготовку среды.

Оба загрузчика содержат код с обращением к `ApiSetSchema.dll`, `ApiSetSchemaExtensions`, `Core Platform Extensions`, `Core Security Extensions`. В отчёте о дизассемблировании установлены RVAs обращения к `ApiSetSchema.dll` (`0x1D783` в 22000, `0x1EB38` в 26100). Назначение всей цепочки вызовов и интерфейс boot-time extension loader **пока не восстановлены**.

## 4. Реестр и хранилища: разница архитектур, не просто ключей

Пересчёт первичных полноразмерных экспортов:

| Исследуемый показатель | Factory OS 22000 | Исследованная 26100 |
|---|---:|---:|
| `SYSTEM` — экспортированные разделы | 32 177 | 38 070 |
| `SYSTEM\CurrentControlSet\Control\StateSeparation` | 672 ключа / 1415 значений | 2 ключа / 0 значений |
| `RedirectionMap\Keys` | 466 ключей **включая корень** (465 потомков; 459 непосредственных правил) | отсутствует |
| `RedirectionMap\Files` | 63 ключа **включая корень** (62 правила) | отсутствует |
| `KeyRedirectionLinks` | 82 ключа **включая корень** (81 потомок) | отсутствует |
| `Services\XRo` | 10 ключей / 118 значений | отсутствует |
| `SYSTEM\...\FeatureManagement` | 6 ключей / 3 значения | 1929 ключей / 5666 значений |
| `Session Manager\ApiSetSchemaExtensions` | 16 дочерних регистраций | 5 дочерних регистраций |

В Factory OS `OSBOOT` содержит 132 экспортированных ключа, `DEVICES` — 2407 записей, из которых `CurrentControlSet` и `ControlSet001` содержат зеркальные 941 пути; после нормализации отчёт отмечает 1466 относительных путей. Отдельные физические файлы `OSBOOT`, `DEVICES` и `OSDATA` подтверждались на `O:`. В 26100 соответствующее PnP-состояние находится внутри обычного `SYSTEM`, а эти отдельные hive-пространства не обнаружены в исследованной штатной конфигурации.

BCD Factory OS 22000 содержит 14 объектов. Основная запись `MAINOS` имеет отдельные элементы `osdevice`, `osdatadevice`, `bspdevice`. Указание `unknown` при offline `bcdedit /store` не является доказательством повреждения BCD. Прямой перенос GPT GUID из Factory OS в новую VM недопустим.

**Ограничение названия «полный реестр»:** большие сравнительные ZIP содержат экспортированные `SYSTEM`, `OSBOOT`, `DEVICES` и `HiveList`, но **не весь реестр обеих ОС** (отсутствуют полноценные SYSTEM+SOFTWARE+SAM+SECURITY для двух ВМ). Для Factory OS отдельно имеются сохранённые `SYSTEM.hiv`, `SOFTWARE.hiv`, `OSDATA.hiv`, `OSBOOT.hiv`, `DEVICES.hiv`, но они не дают полного boot-time trace.

## 5. Исправления к предыдущим выводам

1. **Ошибка размера:** в `WCOS-Winload-Kernel-Extensions-22000-vs-26100-2026-11-06.md` файл `apisetschema-26100.dll` указан как **153 888 байт**; фактический исследованный файл — **152 992 байта**, его SHA-256 `aeaaea67b6c57b4d85cc1d7b724f2ec8fe57aa3210c7aee78b3f40e231fd70f1` совпадает с отчётом. Исправить размер; сравнение `.apiset` подтвердилось.
2. `459` и `465` **не противоречат друг другу**: первое число — непосредственные дети `RedirectionMap\Keys`; второе — все потомки при рекурсивном подсчёте. `466` включает корневой ключ.
3. `366` в сравнении `01-Enum.reg` и `367` в большом экспорте `SYSTEM\CurrentControlSet\Enum` относятся к разным объёмам охвата/учёту корня; нельзя представлять их как два независимо несовместимых набора.
4. Старый `COMPLETE-HANDOFF.zip` (2026-11-05, 78 элементов) хранит **устаревший статус** теста persistence и клонирования. Новые контролируемые тесты в `LATEST-READ-ME.md` и полных сравнениях имеют приоритет.
5. Нет доказательств, что прежний `0x5F SECURITY_INITIALIZATION_FAILED` вызван именно отсутствием `statesepext.sys`, `OSBOOT` или `DEVICES`. Существовал separate first-chance AV `0xC0000005` в `winload!OslGetRootCell` с индексом `0xFFFFFFFF`; причинная связь с `Enabled=1` и механизмом ульев **не изолирована контролируемым сравнением**.
6. Нельзя смешивать данные различных VM: `FOS-KD-Test` (нынешний WinDbg), `FOS-SS-Test` (исторические тесты persistence/registry), оригинальная `FOS`, `Activation01` (26100). Даже если все используют Factory OS 22000, их состояние и дисковые конфигурации могут отличаться.
7. При сравнении XRo и statesepext `26/26`, `62/62`, `21/21` подтверждают только именованные PE-интерфейсы, а не ABI, KS/CI-подпись, семантику callback, `FLTMGR`-режимы и безопасность переноса.
8. `NamespaceSeparation` и `StateSeparation` — разные подсистемы; переключать связанные флаги без карты зависимостей нельзя.

## 6. Пошаговый план с критериями перехода

### Этап A — завершить реконструкцию boot-time extension binding (следующий)

- На отдельной `FOS-KD-Test` и затем `Activation01` **только читать** в boot debugger с корректными `winload_prod.pdb` имена и граф вызовов, относящихся к `ApiSetSchema.dll`, загрузке Core Platform/Security Extensions и связыванию IAT до передачи управления NT.
- Сопоставить источник API Set-файла, список расширений, момент загрузки `statesepext.sys` в 22000 и `cmimcext.sys` в 26100; различать загрузку образа и переназначение импорта.
- **Критерий завершения:** для каждой системы составлена проверяемая последовательность загрузчик → схема → модуль → импорт ядра, с адресами/вызовами и явно отмеченными пробелами. Не изменять BCD или API Set для эксперимента.

### Этап B — восстановить порядок подготовки WCOS state/hives

- На FOS-SS-Test (только чтение) исследовать когда и каким компонентом подключаются `OSDATA`, `OSBOOT`, `DEVICES`, как используются BCD `osdatadevice`/`bspdevice`, кто создаёт `\OSDataRoot`/монтаж и какую роль играют `smss`, `SSBoot`, `FirstBootTasks` и `XRo`.
- Проверить каждое важное правило перенаправления на **реальных** операциях и persistence, а не по наличию в реестре; особое внимание к уже отрицательному тесту SourceProbe.
- **Критерий:** граф boot dependencies, включая источник mutable hives и разделение файлового/реестрового состояния.

### Этап C — матрица совместимости 22000 ↔ 26100

- Проверить вызовы/аргументы Phase0/1/2, ABI, подписи/KMCI, FLTMGR и порядок init; сопоставить реально отсутствующие в 26100 компоненты (`XRo`, `SSBoot`, `FirstBootTasks`) и современную альтернативу, если она есть.
- **Критерий:** каждая зависимость имеет оценку `подтверждена`, `требует изменения/исследования` либо `препятствие`. Нельзя считать совпадения PE-импортов достаточным условием.

### Этап D — спроектировать только минимальный PoC

- Отдельный новый VHDX/Hyper-V Gen2; проверенный откат, хэши базовых PE, валидный исходный образ. Не использовать эталонные VHDX/AVHDX как рабочую копию.
- Контрольная загрузка согласованного 26100 нужна лишь как baseline и **не считается WCOS**.
- Минимальные изменения в порядке зависимости: boot/partition → hives/state roots → extension binding/filters → фактическое state separation. Без бессистемного включения `Enabled=1`.

### Этап E — доказать настоящую WCOS Core

- NT 26100 загружается на Hyper-V Gen2; защищённая запись в MainOS не проходит **по установленной причине**, а OSData/Data доступны для записи.
- Файлы и соответствующие значения реестра живут после нескольких перезагрузок; автоматическая переадресация проверяется конкретными контрольными тестами.
- Storage Spaces и сервисные разделы соответствуют выбранной архитектуре, а не просто носят названия WCOS.
- Испытаны восстановление после сбоя, обслуживание и базовый сценарий обновления без разрушения состояния.
- **Stop/go:** если не удаётся воспроизвести обязательные механизмы с совместимыми компонентами 26100, фиксировать ограничение, не переименовывать обычную Windows в «WCOS 26100».

### Этап F — после Core

Минимальная оболочка / UWP и WinUI, затем совместимость оригинального Santorini/Composer 20279; контейнеризированный Win32 и решение OOBE 20279 — отдельные задачи.

## 7. Следующее одиночное действие

**Только для исследовательской `FOS-KD-Test`**, на следующей остановке в **boot debugger** (`winload!DebugService2`, не `nt!DebugService2`) проверить наличие публичных символов и кандидатов на функции загрузки расширений:

```text
lmvm winload
x winload!*ApiSet*
x winload!*Extension*
x winload!*Platform*
```

Эти команды ничего не изменяют. Если PDB недоступен или wildcard не находит имён, не делать вывод, что таких функций нет; использовать известные static RVA и дизассемблирование с развёртыванием ближайшей функции. Начать дальнейший граф загрузчика можно только после фиксации этого вывода.

**Не делать пока:** `Enabled=1` на 26100, перенос `statesepext.sys`/`XRo.sys` из 22000 в работающую 26100, замену `apisetschema.dll`, редактирование оригинальных BCD/улей/WinSxS, изменение Secure Boot/CI ради обхода проверки, тесты на эталонной `FOS`.

## 8. Предел уверенности

Высокая уверенность: наблюдения WinDbg, хэши, структура API Set, наличие/отсутствие экспортированных реестровых конфигураций. Средняя: интерпретация назначения некоторых кодовых ветвей winload/SMSS на основе строк и PDB. Низкая/не установлено: безопасная совместимость 22000-драйверов с 26100, первопричина 0x5F, возможность полноценного WCOS servicing на 26100, дата/объём первого успешного PoC. **Готовой работающей WCOS 26100 пока нет; проценты готовности из старых handoff субъективны и не являются техническим показателем.**
