# Причина расхождения: статус доказательств

**INFERRED (для показанной загрузки):** если гостевая копия действительно побайтно совпадала с B-DualSize, итоговый пустой Trace Host объясняется тем, что правка затронула legacy v6 `VALUE_ENTRY` и добавила строку за пределами объявленных блоков встроенного представления 7, тогда как `winload` компонует и разрешает именно представление 7 и затем обрабатывает динамическое расширение Trace; точное происхождение каждого байта итоговой схемы в этой загрузке остаётся **UNKNOWN**, поскольку не сняты хеш гостевой копии и промежуточные буферы.

## Основание

- Проверены все 69 строк `FILE-MANIFEST.csv`: размеры и SHA-256 совпали. Существенные образы: оригинал 26100.9278 `391a2818fdef14f4a9b6e6ce2a7e7f01d04f943de9ef543ec683927cfe480889`; A `67b15197c5edc07fe5a2653461a1740d17ac6d6dadbbea2971c1d409781132a3`; B `ba382268c00918b4a99b2efe3577782673aa6be58e7b567a776e43fca21583f9`; `winload.efi` 26100.9444 `1c1a978448b8e0fc2284c13d6e55fde8bf9827dca432cdc8a9be66c2e729adda`. Это идентичность **приложенных** файлов, а не файла на диске VM.
- В B `.apiset` начинается по file offset `0x2000` (RVA `0x3000`), namespace `Size=0x29C84`; legacy Trace value по namespace `+0x94F0` / file `0xB4F0` имеет HostOffset `0x29C60`, HostLength `0x24`, а UTF-16 строка лежит по file `0x2BC60`. Все 984 v6 hash entries и 990 value entries проходят проверку границ; 984 хеша совпали с именами.
- Встроенный заголовок 7 начинается по namespace `+0x1C`, его `Size` находится по `+0x20`. В B он равен `0x29C84`, однако конец объявленных им блоков остаётся `0x29C00 + 0x60 = 0x29C60`. Вся область полезных блоков `+0xC8F0..+0x29C60` в B совпадает с оригиналом; legacy value `+0x94F0` лежит до неё, вставленная строка — после неё. Это показывает, почему наличие корректной v6 записи само по себе не меняет источник для resolver.
- Код именно данного `winload.efi`: `ApiSetComposeSchema` RVA `0x27958B–0x2795AD` выбирает `ApiSetComposeSchema_V7` RVA `0x27AA24` при v6 wrapper с маркером 7 по `+0x1C`; `ApiSetResolveToHost` RVA `0x279181–0x27919F` при `+0x1E & 4 == 0` направляет запрос в RVA `0x27A60C`. В приложенном файле `+0x1E=0x08`, условие выполнено.
- `ApiSetComposeSchema_V7` выделяет новый буфер (`0x27AB2E`), рассчитывает его размер по таблицам (`0x27BEFC`) и публикует новый указатель/размер (`0x27ABF0–0x27AC03`), а не использует всю `Namespace.Size` как длину копии. Для исходных счётчиков расчёт равен `0x29C60`; ветка добавления 20-байтной записи (`0x27C5D6`) даёт `0x29C74`, что точно совпадает с живым дампом. Статическая таблица динамических расширений по RVA `0x2B2DB0` содержит Trace и `dtrace.sys`; при ложном predicate код берёт пустую UTF-16 строку по RVA `0x2BABF8` (`0x23023–0x23034`) и в любом случае строит расширение (`0x23056–0x23076`). Значение predicate в данном boot не записано, поэтому конкретную ветку выводим из итогового состояния, а не называем непосредственно наблюдённой.
- Живой WinDbg дамп той же Trace-загрузки: `OslApiSetSchema=0xfffff802344ccd20` по `winload+0x354F00`; итоговые `Size=0x29C74`, `Count=984`; legacy Trace value `+0x94F0` имеет HostOffset `0x1F304`, HostLength `0`; `UNICODE_STRING` результата содержит `Length=MaximumLength=0`, `eax=0`, resolved marker `1`. Поиск `WcosTraceSmoke.sys` по итоговым `0x29C74` байтам не дал результата. Адрес `schema+0x1F304` при нулевой длине не является строкой Host.

**Граница вывода:** из кода и байтов доказан механизм, способный дать именно эти значения. По одному конечному снимку нельзя исключить другое содержимое гостевой копии или промежуточное registry extension. Поэтому утверждение «именно V7-компоновщик удалил Host из конкретного буфера B» пока не доказано. SEALED к Trace не относится: у Trace Entry.Flags=0.
