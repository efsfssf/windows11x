# Windows 11X — сопоставление аппаратного реестра Factory OS 22000 и Windows IoT LTSC 26100

Дата: 6 ноября 2026. Статус: статическая инвентаризация, **не** доказательство работоспособной State Separation на NT 26100.

## Источники и методика

- Factory OS 22000: `07-DEVICES.reg` (экспорт `HKLM\DEVICES`, UTF-16LE, 2 339 182 байта); материал получен из экспериментальной копии FOS-SS-Test.
- Windows 11 IoT Enterprise LTSC 26100: `WCOS-Reg-26100-Devices.zip` (6 `.reg`-файлов, один `.csv`).
- Парсинг `.reg` с учётом заголовков разделов, значений и продолжений многострочных `hex:`; ключи и имена значений сравнивались без учёта регистра. Сопоставление производится **по относительным путям**, без попытки связывать разные GUID экземпляров устройств.
- Для DEVICES использовался `ControlSet001`; для 26100 — `CurrentControlSet`. Это сопоставление разных виртуальных машин с разным состоянием PnP. Число совпадений не характеризует совместимость ядра.

## Проверка содержимого архива 26100

| Файл | Ключи | Значения |
|---|---:|---:|
| `01-Enum.reg` | 366 | 1 419 |
| `02-DeviceClasses.reg` | 389 | 167 |
| `03-HardwareConfig.reg` | 13 | 154 |
| `04-DriverDatabase.reg` | 13 559 | 29 613 |
| `05-Networking-NSI.reg` | 61 | 15 |
| `06-COM-Arbiter.reg` | 2 | 3 |

Файл `07-VirtualSwitch.reg` отсутствует. **Это не доказательство отсутствия соответствующего сервиса или ключа**: возможны отсутствие ключа, отказ экспортирования, иная конфигурация ВМ. Файл `00-ExportResults.csv` оказался некорректным для диагностики: заголовок `Length`, повторяющиеся 37/0 вместо ожидаемых `Name,RegistryPath,ExitCode,Exported`. Вероятная причина — stdout `reg.exe export`, попавший в массив `$results`, и формирование CSV по первому элементу. Статус отдельных `reg export` по CSV определить нельзя; шесть экспорта реально содержатся в ZIP.

## Структурное сравнение

| Область | Factory OS 22000: откуда сравнивали | Factory: ключи / значения | Windows 26100: откуда сравнивали | 26100: ключи / значения | Общие относительные ключи | Полностью идентичные наборы значений среди общих |
|---|---|---:|---|---:|---:|---:|
| PnP Enum | `DEVICES\ControlSet001\Enum` | 548 / 2 451 | `SYSTEM\CurrentControlSet\Enum` | 366 / 1 419 | 168 | 123 |
| Интерфейсы устройств | `DEVICES\ControlSet001\Control\DeviceInterfaces` | 342 / 149 | `SYSTEM\CurrentControlSet\Control\DeviceClasses` | 389 / 167 | 109 | 109 |
| HardwareConfig | `DEVICES\HardwareConfig` | 13 / 154 | `SYSTEM\HardwareConfig` | 13 / 154 | 4 | 2 |
| DriverDatabase | `DEVICES\DriverDatabase` | 2 / 2 | `SYSTEM\DriverDatabase` | 13 559 / 29 613 | 1 | 0¹ |
| NSI | `DEVICES\Networking\Nsi\PersistentStore` | 68 / 37 | `SYSTEM\CurrentControlSet\Control\Nsi` | 61 / 15 | 59 | 51 |
| COM arbiter | `DEVICES\ControlSet001\Control\COM Name Arbiter` | 1 / 0 | `SYSTEM\CurrentControlSet\Control\COM Name Arbiter` | 2 / 3 | 1 | 0 |

¹ У общего корневого ключа DriverDatabase есть два совпадающих параметра `Version` и `SchemaVersion`, но 26100 дополнительно содержит собственные параметры, поэтому весь набор значений корневого ключа не идентичен.

### PnP Enum

В обоих снимках присутствуют ACPI, ROOT, VMBUS, STORAGE, SCSI, DISPLAY, SWD и другие классы перечисления устройств. В Factory OS больше экспортированных записей VMBUS/STORAGE, в Windows 26100 есть дополнительные ветки типов терминального ввода, удалённого отображения и др. Это различие может зависеть от конкретной конфигурации ВМ, версии Windows и истории установленных устройств. Из 168 совпадающих относительных путей 123 содержат одинаковые наборы значений.

### DeviceInterfaces versus DeviceClasses — значимый результат

Несмотря на различие **имён веток**, ключи обоих экспортов имеют однотипную структуру: GUID класса интерфейса → экземпляры с `##?#...` → подразделы `#`. Для 109 совпадающих относительных путей значения совпали полностью. Следовательно, эти области сопоставимы по содержимому в имеющихся снимках. Это **не** означает, что существует универсальное правило прямой замены имен или что 26100 автоматически может загрузить отдельный DEVICES.

### HardwareConfig

Число ключей и значений в двух экспортированных ветках совпадает (13 и 154), а `LastId` равен `2` в обоих корнях. GUID конфигураций различаются; это ожидаемо для разных установок. Совпадают четыре относительных пути, из них два полностью по значениям. Здесь наглядно просматривается сходная схема хранения аппаратной конфигурации в разных пространствах реестра.

### DriverDatabase — важное ограничение

В Factory OS в **экспортированном DEVICES** присутствуют только корневой `DriverDatabase` и `Updates`, всего 2 ключа. В 26100 под **SYSTEM** обнаружено 13 559 ключей, включая многочисленные `DriverPackages`, `DeviceIds` и `DriverInfFiles`.

**Нельзя заключить**, что полная база драйверов «исчезла» из Factory OS или «перенесена» целиком в DEVICES. Для этого ещё надо выяснить, где расположен полный `SYSTEM\DriverDatabase` и какие данные хранятся в доступном runtime-представлении Factory OS (возможно, часть данных находится в другой базе/образе).

### NSI

Совпадает 59 из 68 относительных ключей Factory OS и 61 ключа Windows 26100. Из них 51 имеет идентичные значения (с учётом пустых разделов). Это близкое соответствие структуры `DEVICES\Networking\Nsi\PersistentStore` и обычной ветки `SYSTEM\...\Control\Nsi`, но **не** экспериментальное доказательство, что каждое обращение перенаправляется во время работы.

### COM Name Arbiter

У Factory OS экспортированный корень есть, но без значений. У 26100 присутствует `ComDB` и дочерняя ветка `Devices`. Результат зависит от фактически установленных COM-портов и устройств. `DEVICES\ControlSet001\Control\COM Name Arbiter` нельзя просто подменять содержимым 26100.

## Как это меняет выводы о WCOS 26100

1. Отдельный DEVICES в Factory OS действительно содержит PnP Enum, аппаратные конфигурации, интерфейсы устройств, NSI и часть связанного состояния. Соответствующие структурные данные в стандартной 26100 находятся в обычном SYSTEM.
2. Структура данных в ряде областей близка вплоть до совпадения относительных путей и значений; различие **в размещении и механике предоставления пространства реестра** существенно для State Separation.
3. Нельзя переносить DEVICES целиком или удалять соответствующие ветки SYSTEM в 26100: не доказаны совместимость ранней загрузки, правила перенаправления, обслуживание, PnP-инициализация и защита MainOS.
4. Этот экспорт не содержит событий загрузки и не объясняет напрямую `SECURITY_INITIALIZATION_FAILED (0x5F)` либо first-chance `0xC0000005` в `winload!OslGetRootCell`.
5. Число ключей — статистика экспортированных снимков, а не измерение независимого дискового состояния ульев.

## Следующая точечная проверка без изменений системы

На `FOS-SS-Test` через SSH:

```cmd
reg query "HKLM\SYSTEM\DriverDatabase"
reg query "HKLM\SYSTEM\CurrentControlSet\Control\DeviceClasses"
```

На исправной `Activation01` (26100):

```cmd
reg query "HKLM\SYSTEM\CurrentControlSet\Control\DeviceInterfaces"
```

Эти запросы помогут отличить реальное перемещение дерева в DEVICES от различия имён и локальных представлений. Пока не повторять `StateSeparation\Policy\Enabled=1`.
